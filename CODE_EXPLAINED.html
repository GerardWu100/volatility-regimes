The project in plain English

An option chain shows what the market charges for insurance today. This project turns each day's chain into seven numbers that describe its pricing, groups the days into a small number of unlabelled states with a statistical clustering model, and asks one focused question: does knowing today's state improve forecasts of the index's volatility over the next month compared with four simpler rules? It answers that question twice: once over the full history to describe the data, and once by retraining on past data at each step for an out-of-sample score.

01The question and the two ways it is answered

The repository centres on one question from README.md:

In plain words

Do hidden states in the option-implied volatility surface help forecast the index's volatility next month better than simple rules?

Two code paths answer it, but they serve different purposes.

LayerEntry pointWhat it doesCan its numbers be traded on?
Descriptivepipelines/descriptive_pipeline.py Fits regimes once on the full history, then describes each one: its duration, surface, and subsequent returns. No The labels use the full sample. See limitations.
Walk-forwardwalkforward/engine.py Moves through time. At each step it refits on past data only, forecasts the next five days, and records the error. In principle The leakage controls are real, but the current data is not real market data.
Terms used throughout

Implied volatility (IV) — the volatility value that makes an option-pricing formula match the option's market price. It is the market's annualized forecast of future movement.
At-the-money (ATM) — near where the option's delta is $0.50$ in absolute value; the option is roughly as likely to finish in the money as out of the money.
Delta — how much the option price moves per one-dollar move in the index. Calls have positive delta, puts negative. It is used here as a scale-free way to say "how far from at-the-money", so the same feature means the same thing whether the index is at 1,000 or 5,000.
Realized volatility (RV) — the volatility that occurred, measured after the fact from daily returns.
Regime — a group of days that a clustering model judged similar. The model is not told what a regime means.
Look-ahead (leakage) — using information that would not have been available when the forecast was made.

04Data in — data_access/loader.py

In plain words

Read the option chain and daily closing prices. Use the files in data/raw/ first; use the database only if they are missing or fail integrity checks.

What it does

Input: a symbol, start and end dates, and the [cache] settings. Output: two DataFrames (tables of rows and columns): options with nine columns, and prices with date and close. Role: the only code that accesses storage. Downstream code receives clean frames and does not need to know their source.

The offline check asks more than whether the file exists. _build_cache_validation_result runs four checks in order and stops at the first failure:

  1. Version — the sidecar's metadata_version must match the configured version.
  2. Schema — the sidecar and Parquet column lists and data types must agree, and each type must be allowed.
  3. Row count — the count in the sidecar must equal the actual row count.
  4. Date coverage — the sidecar's first and last dates must match the file and cover the requested window.

SPX and SPXW are ticker symbols for overlapping contracts. _normalize_options_dataframe sorts by (trade_date, expiry_date, option_type, strike_price, open_interest) with open interest descending, then keeps the first row in each group. The database fallback reports the exact folder, filenames, and database error instead of only a connection stack trace. This helps when a fresh clone has a valid cache but no .env: the message shows that the repository itself is fine.

05Features — features/surface.py

In plain words

Reduce each day's option chain to seven numbers: the cost of insurance, the difference between downside and upside protection, the curvature across strikes, and the change in insurance cost with time to expiry.

What it does

Input: the cleaned options frame. Output: a DataFrame indexed by trade_date with seven float columns, in this order: atm_iv_near, skew_near, butterfly_near, atm_iv_mid, skew_mid, butterfly_mid, term_slope. Role: every regime model clusters this feature vector.

How it works

For each trade date, _select_expiry picks one near-term expiry: the one closest to 30 days within the 15–45 window. It also picks one mid-term expiry closest to 90 days within 45–120. For each expiry, _extract_features_one_expiry obtains three values by interpolating across delta. The seventh feature is the difference between the two at-the-money values.

The formula

Let $\sigma(\Delta)$ be implied volatility at delta $\Delta$, read off one expiry's chain. Between two quoted strikes it is interpolated in a straight line:

$$\sigma(\Delta)=\sigma_{\text{lo}}+\bigl(\sigma_{\text{hi}}-\sigma_{\text{lo}}\bigr)\cdot \frac{\Delta-\Delta_{\text{lo}}}{\Delta_{\text{hi}}-\Delta_{\text{lo}}}$$

The four features per expiry use $a$, the atm_delta setting, and $w$, the wing_delta setting:

$$\begin{aligned} \mathrm{atm\_iv} &= \sigma(-a) \\ \text{skew} &= \sigma(-w)-\sigma(+w) \\ \text{butterfly} &= \tfrac{1}{2}\bigl[\sigma(-w)+\sigma(+w)\bigr]-\sigma(-a) \\ \mathrm{term\_slope} &= \mathrm{atm\_iv}_{\text{mid}}-\mathrm{atm\_iv}_{\text{near}} \end{aligned}$$

$\Delta_{\text{lo}}$ and $\Delta_{\text{hi}}$ are the quoted deltas immediately below and above the requested value; $\sigma_{\text{lo}},\sigma_{\text{hi}}$ are their implied volatilities. Negative deltas are puts and positive deltas are calls, so $\sigma(-a)$ is read from puts and $\sigma(+w)$ from calls. Skew is positive when downside protection costs more than upside protection, the usual equity-index shape. Butterfly is positive when the wings cost more than a straight line between them suggests, meaning the market charges extra for large moves in either direction. Term slope is positive when longer-dated insurance costs more than short-dated insurance.

Why delta space and not strike space

A strike of 1,060 means something different in 2010 and 2024. A delta of $-0.50$ has the same meaning in both years. Using delta makes the seven features comparable across the sample, which makes clustering fifteen years of days defensible.

Trap

interpolate_iv_at_delta returns NaN instead of extrapolating outside the quoted range. That avoids inventing wing volatility, but a thin chain then produces a blank feature row, which both pipelines drop. Check the log line Feature extraction complete: N days, M valid; otherwise a run that loses many days can look like one that loses none.

06The forecast target — walkforward/targets.py

In plain words

For each trading day, measure the index's volatility over the following twenty trading days. That is the value every model forecasts.

What it does

Input: the price frame, the feature frame (used only for its index and atm_iv_near column), a horizon $h$, and an annualization factor $A$. Output: a frame on the feature index with realized_vol, variance_risk_premium, and forward_return. Role: supplies the actual values used to score each forecast.

The formula

$$r_t=\log\!\left(\frac{P_t}{P_{t-1}}\right)$$

$$\mathrm{RV}_t(h)=\operatorname{std}\bigl(r_{t+1},\,r_{t+2},\,\ldots,\,r_{t+h}\bigr)\times\sqrt{A}$$

$$\mathrm{VRP}_t=\sigma^{\mathrm{ATM}}_t-\mathrm{RV}_t(h),\qquad \mathrm{fwd\_ret}_t=\frac{P_{t+h}}{P_t}-1$$

$P_t$ is the closing index level on trading day $t$; $r_t$ is that day's log return; $h$ is the horizon in trading days (default 20); $A$ is trading days per year (252); $\operatorname{std}$ is the sample standard deviation with $h-1$ in the denominator, which is what pandas.rolling().std() computes; $\sigma^{\mathrm{ATM}}_t$ is atm_iv_near on day $t$. The variance risk premium is the gap between the volatility price and the volatility that occurred. A positive value means insurance cost more than the subsequent realized volatility.

The one line that does the alignment

log_returns = np.log(close_series / close_series.shift(1))
rolling_std = log_returns.rolling(window=horizon).std()
annualized_vol = rolling_std * np.sqrt(float(annualization))

# Shift the trailing window backward so the value lands on the start date
# of the forward-looking window.
forward_realized_vol = annualized_vol.shift(-horizon)

rolling(20).std() produces a backward-looking value: on day $t$ it is the standard deviation of $r_{t-19}\ldots r_t$. Shifting by $-20$ moves it 20 rows earlier, to day $t-20$, where it describes $r_{t-19}\ldots r_t$, the twenty returns after $t-20$. After renaming the index, the value on day $t$ describes $r_{t+1}\ldots r_{t+h}$, as required.

Because the target is shifted, the last $h$ rows have no answer and are later dropped by dropna(). Capacity checks must use the rows that survive, not the number of feature rows. Using the larger count can make a walk-forward run write an empty file; the repository now checks for this explicitly.

07Splits and the embargo — walkforward/splits.py and the engine

In plain words

Move through the calendar. Train on data before today, forecast the next five days, move forward five days, and repeat. Then remove the most recent training days because their outcomes were not known on the forecast date.

Step one: the plain chronological split

splits: list[WalkForwardSplit] = []
train_end = min_train_size

while train_end < len(dates):
    test_start = train_end
    test_end = min(test_start + step_size, len(dates))

    # Training always uses everything strictly before the test window.
    train_index = dates[:train_end]
    test_index = dates[test_start:test_end]
    splits.append(WalkForwardSplit(train_index=train_index, test_index=test_index))

    # Expand the history by the same stride used for testing.
    train_end = test_end

This is an expanding window: the training set only grows. The same file also contains a fixed-length rolling-window builder, but the engine does not use it.

Step two: the embargo, which is the part that matters

The formula

Let $i(d)$ be the position of date $d$ in the full sorted price history, $h$ the horizon, and $s$ the first date of the test block. A training row at date $t$ is kept only when

$$i(t)+h \;<\; i(s)$$

The label at $t$ uses returns $r_{t+1}\ldots r_{t+h}$, so its last price is at position $i(t)+h$. Requiring that position to be strictly before $i(s)$ prevents a training label from using a price observed on or after the first forecast day. Positions come from the price calendar, not the feature calendar, so missing option data cannot narrow the gap.

Why chronological ordering is not enough on its own

This is the key idea in the repository. Suppose training ends on Friday and the forecast starts on Monday. Friday's label describes the next twenty trading days, including Monday and the three weeks after it. Training on Friday would give the model part of the answer in advance. The split is chronological but still contaminated. The embargo removes the last $h$ training rows to prevent that overlap.

Across the SPX panel's 3,872 aligned rows, the builder proposes 271 splits. After the embargo, 267 still have the required 2,520 safe labels, so the first forecast is 2019-10-28, not 2019-09-30. Those 267 splits contain 1,332 forecast dates per model: 266 full blocks of five and a final block of two because the panel ends before the last stride completes. 1,332 is the count in outputs/reports/walkforward/metric_summary.csv.

Trap

min_train_size is checked after the embargo. The split builder receives the same number, so the first splits are proposed and then skipped because they lack roughly $h$ rows. That is why the first forecast date is about a month later than simple arithmetic suggests. Before fitting any model, _maximum_safe_train_size puts the last row in a one-row test set and measures the largest embargoed training set that could ever exist; if that is smaller than min_train_size, the run raises a ValueError naming the symbol, horizon, feature set, aligned row count, maximum, and requested minimum instead of writing an empty CSV.

08The regime models — regimes/latent_models.py

In plain words

Given daily feature vectors, find a small number of overlapping groups that describe the data and assign each day to the group it most likely belongs to. Then rename the groups so that 0 is always the calmest one.

The Gaussian Mixture Model — fit_gmm

The model

Each standardized (rescaled to a common scale) daily feature vector $x_t\in\mathbb{R}^d$ is assumed to be drawn from one of $K$ multivariate normal distributions, but you are not told which:

$$p(x_t\mid\theta)=\sum_{k=1}^{K}\pi_k\,\mathcal{N}\!\bigl(x_t\mid\mu_k,\Sigma_k\bigr)$$

$K$ is the number of regimes; $\pi_k$ is the share of days in regime $k$, with $\sum_k\pi_k=1$; $\mu_k$ is the regime's average feature vector; $\Sigma_k$ is its $d\times d$ covariance matrix (the code uses covariance_type="full", so each regime has its own unrestricted shape); $\mathcal{N}$ is the multivariate normal density; and $\theta=\{\pi_k,\mu_k,\Sigma_k\}$ is the full parameter set. The model treats days as independent, so it has no notion of yesterday.

The objective it maximizes

$$\ell(\theta)=\sum_{t=1}^{n}\log\sum_{k=1}^{K}\pi_k\,\mathcal{N}\!\bigl(x_t\mid\mu_k,\Sigma_k\bigr)$$

$n$ is the number of training days. The log-likelihood measures how probable the observed data is under the parameters. Because the regime for each day is unknown, the maximum is found iteratively rather than from a single formula.

The update the loop performs (expectation-maximization)

E step — given the current parameters, work out how much each day belongs to each regime:

$$\gamma_{tk}=\frac{\pi_k\,\mathcal{N}(x_t\mid\mu_k,\Sigma_k)} {\sum_{j=1}^{K}\pi_j\,\mathcal{N}(x_t\mid\mu_j,\Sigma_j)}$$

M step — given those weights, recompute the parameters as weighted averages:

$$n_k=\sum_{t=1}^{n}\gamma_{tk},\qquad \pi_k=\frac{n_k}{n},\qquad \mu_k=\frac{1}{n_k}\sum_{t=1}^{n}\gamma_{tk}\,x_t$$

$$\Sigma_k=\frac{1}{n_k}\sum_{t=1}^{n}\gamma_{tk}\,(x_t-\mu_k)(x_t-\mu_k)^{\top}$$

$\gamma_{tk}$ is the responsibility of regime $k$ for day $t$, a number from 0 to 1 with $\sum_k\gamma_{tk}=1$; $n_k$ is the effective number of days in regime $k$; and $\top$ means matrix transpose. The steps alternate until the log-likelihood stops rising. Each step cannot lower it, but the result depends on the starting point. That is why the code uses n_init=5 and random_state=42: five starting points, with the best fit kept and the same answer on every run.

Choosing the number of regimes

The code fits every $K$ from min_k to max_k and keeps the one with the lowest Bayesian information criterion:

$$\mathrm{BIC}(K)=p_K\log n-2\,\ell_K,\qquad p_K=(K-1)+Kd+K\frac{d(d+1)}{2}$$

$\ell_K$ is the best log-likelihood reached with $K$ regimes. $p_K$ counts the free parameters: $K-1$ mixing weights, $Kd$ mean entries, and $K$ symmetric covariance matrices with $d(d+1)/2$ distinct entries each. The $p_K\log n$ term penalizes complexity, so extra regimes must improve the fit enough to justify themselves. Lower is better.

The Hidden Markov Model — fit_hmm

The model, its objective, and its update

Model. A hidden state $z_t\in\{1,\ldots,K\}$ moves according to a transition matrix. The observed features are normally distributed around that state's mean:

$$\Pr(z_{t+1}=j\mid z_t=i)=A_{ij},\qquad x_t\mid z_t=k\;\sim\;\mathcal{N}(\mu_k,\Sigma_k)$$

Objective. The same idea as before, but the sum runs over complete state paths:

$$\ell(\theta)=\log\sum_{z_1,\ldots,z_T}\Pr\bigl(z_1,\ldots,z_T,\;x_1,\ldots,x_T\mid\theta\bigr)$$

Update (Baum-Welch, the expectation-maximization method for this model). A forward-backward pass gives $\gamma_t(k)=\Pr(z_t=k\mid x_{1:T})$ and $\xi_t(i,j)=\Pr(z_t=i,z_{t+1}=j\mid x_{1:T})$. The parameters are then re-estimated as

$$A_{ij}=\frac{\sum_{t=1}^{T-1}\xi_t(i,j)}{\sum_{t=1}^{T-1}\gamma_t(i)},\qquad \mu_k=\frac{\sum_{t=1}^{T}\gamma_t(k)\,x_t}{\sum_{t=1}^{T}\gamma_t(k)}$$

$T$ is the sequence length; $A_{ij}$ is the probability of moving from state $i$ to state $j$ in one day; $\gamma_t(k)$ is the probability that day $t$ was in state $k$; and $\xi_t(i,j)$ is the probability that day $t$ was in $i$ and day $t+1$ was in $j$. Both quantities use the whole sequence $x_{1:T}$, including days after $t$. That creates the look-ahead problem discussed in limitations.

The code fits the model n_restarts times with different random seeds, scores each fit by in-sample log-likelihood, and keeps the best. Failed restarts are logged as warnings and skipped; if all fail, it raises RuntimeError. Labels come from Viterbi decoding, which returns the most likely complete state path rather than the most likely state for each day independently.

HMM restart 9 failed: 'covars' must be symmetric, positive-definite

Six of the ten restarts collapse, and two of the four survivors also log Model is not converging. The final result therefore comes from only a few fits. The output files do not record this; it appears only as console warnings. Lowering hmm_random_restarts would reduce the pool and could select a different five-state result. The run remains deterministic because restart $i$ uses seed $i$.

Fixing label switching — order_regimes_by_volatility

Why this function has to exist

A clustering model is free to call the calm group "0" or "1". Refit the same data with another seed and the labels may swap, making label-based statistics hard to compare. This function computes each label's average standardized atm_iv_near, sorts the labels, and renumbers them so 0 is always the lowest-volatility regime. Only then are labels comparable across splits, symbols, and runs.

09The five forecast rules — walkforward/models.py

In plain words

Five ways to answer “how volatile will the next month be?”, from today's option price to the historical average for today's regime.

Row nameRuleUsesWhy it is in the panel
atm_iv$\hat y_t=\sigma^{\mathrm{ATM}}_t$today's option price only The market's own forecast: the basic result to beat.
historical_mean$\hat y_t=\dfrac{1}{|\mathcal{T}_t|}\sum_{u\in\mathcal{T}_t}y_u$past labels only The hardest benchmark to beat. If a complex model cannot beat a flat line, it adds nothing.
trailing_realized_vol$\hat y_t=\operatorname{std}(r_{t-h+1..t})\sqrt{A}$past prices only Tests whether recent volatility persists.
linear_featuresordinary least squares on the selected featurespast features and labels Tests whether the surface helps before using regimes.
gmm_regime_mean$\hat y_t=\bar y^{(\hat z_t)}$past features and labels Tests the project's main claim.
The formula for the regime forecast

$$\hat y_t=\frac{1}{\bigl|\{u\in\mathcal{T}_t:\hat z_u=\hat z_t\}\bigr|} \sum_{u\in\mathcal{T}_t,\;\hat z_u=\hat z_t}y_u$$

$\mathcal{T}_t$ is the embargoed training window available on day $t$; $y_u$ is the realized-volatility label for training day $u$; $\hat z_u$ is the ordered regime assigned to training day $u$; and $\hat z_t$ is the ordered regime assigned to the forecast day. In practice, the code finds the regime that resembles today's features and predicts the average outcome after matching training days. If today's regime cannot be mapped, it uses the training mean and records the regime as $-1$.

How the block fit works

train_feature_matrix = train_features.to_numpy(dtype=float)
standardized_train_features, fitted_scaler = standardize_features(
    feature_matrix=train_feature_matrix
)
ordered_test_features = test_features.reindex(columns=train_features.columns)
standardized_test_features = fitted_scaler.transform(
    ordered_test_features.to_numpy(dtype=float)
)
Why the scaler is fitted and then reused, never refitted

Standardizing means subtracting the mean and dividing by the standard deviation. Computing those values from the training and test rows together would leak test information into training. Fitting on training rows only and calling .transform() on test rows preserves the boundary. In the first window, the fitted mean is [0.14023, 0.16224, 0.02202] and scale is [0.03557, 0.03558, 0.00251]; every test row uses them.

Why one fit per block instead of one per day

All five test days in a block use the same training window, so refitting five times would produce the same models. One fit gives the same answer for the linear and mixture models and is five times faster.

Trap the Hidden Markov Model path avoids

The mixture model can classify each test day independently, but a Markov model uses sequences and needs context. Decoding the full training and test blocks at once would let Wednesday's observation influence Monday's state. The code instead decodes the training sequence plus one test row at a time and keeps only the final state:

predicted_test_labels = np.asarray(
    [
        int(
            fitted_model.predict(
                np.vstack([standardized_train_features, test_feature_row])
            )[-1]
        )
        for test_feature_row in standardized_test_features
    ],
    dtype=int,
)

Element [-1] makes this safe: the last state uses observations up to that point and has no later observation to condition on. It is slow, requiring one decode per test day, but that is the cost of the guarantee.

10The engine loop — walkforward/engine.py

In plain words

Four nested loops: for each symbol, horizon, feature set, and time step, fit, forecast, and write five rows per day.

What it does

Input: the experiment grid and shared configuration. Output: three files in outputs/reports/walkforward/. Role: defines what a run does.

The order of operations, once per symbol and horizon

  1. Load options and prices, build the seven features, and drop blank rows.
  2. Build the forward targets and trailing-volatility benchmark on the feature index.
  3. Join features, target, and benchmark into one frame and call dropna(). Every model then sees exactly the same dates, making the error comparison fair.
  4. Check capacity. If the largest possible embargoed training set is smaller than min_train_size, raise a ValueError before fitting anything.
  5. Build expanding splits, apply the embargo to each, and skip any with too few safe labels.
  6. Fit the linear and mixture models once per block, and compute the historical mean once.
  7. Walk the test rows and append five standardized dictionaries per row.
Why the shared aligned panel matters more than it looks

Step 3 makes the comparison fair. If the trailing-volatility benchmark had extra dates because it needs fewer inputs, it would be scored on a different sample and its root mean squared error would not be comparable. Joining first and dropping blanks once gives every model the same dates.

Trap

OUTPUT_DIR is a module-level global. main() reassigns it from walkforward.toml before calling run_research, and run_research reads the global instead of taking a parameter. If you import run_research and call it directly, as the tests and notebook do, the output_dir setting in walkforward.toml is ignored and results go to the default folder.

11Scoring — walkforward/reporting.py

The formulas

For $N$ forecast dates with actual values $y_t$ and forecasts $\hat y_t$:

$$\mathrm{MSE}=\frac{1}{N}\sum_{t=1}^{N}\bigl(y_t-\hat y_t\bigr)^2,\qquad \mathrm{RMSE}=\sqrt{\mathrm{MSE}},\qquad \mathrm{MAE}=\frac{1}{N}\sum_{t=1}^{N}\bigl|y_t-\hat y_t\bigr|$$

And, for a model $m$ against a benchmark $b$ measured on identical dates:

$$R^2_{\mathrm{OOS},\,m\mid b}=1-\frac{\mathrm{MSE}_m}{\mathrm{MSE}_b}$$

$\mathrm{MSE}$ is mean squared error; $\mathrm{RMSE}$ is its square root, in volatility units; and $\mathrm{MAE}$ is mean absolute error. $R^2_{\mathrm{OOS}}$ is positive when the model's squared error is smaller than the benchmark's, zero when they tie, and negative, without a lower bound, when the model is worse. It is not regression $R^2$ and is not limited to $[0,1]$.

The function groups the panel by (symbol, horizon, feature_set, model_name) and computes each benchmark's mean squared error over the matching (symbol, horizon, feature_set) group. A model is therefore compared only with a benchmark scored on the same dates. The two benchmarks are atm_iv and historical_mean.

Why two benchmarks and not one

Scoring only against implied volatility makes every model look good. Implied volatility is usually higher than realized volatility because it includes a risk premium, so an unbiased rule can beat it. The expanding historical mean has no such bias and is the fairer hurdle. In the run under outputs/, every model beats the first hurdle by a wide margin, but none beats the second.

Trap in the markdown summary

write_research_summary sorts the full table by root mean squared error and prints the top ten. Root mean squared error uses the target's units, so a 5-day horizon, a 60-day horizon, and different indices are not on the same scale. The ranking is fine for one symbol and horizon; with more than one, the "best configurations" table compares incompatible values.

12The descriptive layer — descriptive/analytics.py

In plain words

Fit regimes once on all fifteen years, then describe their duration, insurance cost, and subsequent index returns.

The pipeline uses a mixture model to choose the number of regimes, fits a Markov model with that count, orders the states by volatility, rebuilds the transition matrix from the renamed path, and passes the labels to six reporting functions.

FunctionProduces
regime_summary_statsmean and standard deviation of every feature inside each regime, plus day counts and shares
regime_vrp_statsaverage variance risk premium per regime with a 95% interval, $\bar x \pm 1.96\,s/\sqrt{n}$
regime_transition_statsaverage unbroken run length per regime, total number of switches, switch rate
predictive_regressionordinary least squares of forward realized volatility on ATM implied volatility plus regime dummy variables, with the lowest regime as the omitted baseline
forward_returns_by_regimemean, standard deviation and annualized Sharpe ratio of the $h$-day forward return inside each regime
_recompute_transition_matrix_from_labels
lives in pipelines/descriptive_pipeline.py, not in analytics.py		counts one-step transitions on the renamed path and normalizes each row
The Sharpe formula used here

$$\mathrm{Sharpe}=\frac{\bar R_h}{s_h}\sqrt{\frac{A}{h}}$$

$\bar R_h$ and $s_h$ are the mean and standard deviation of the $h$-day forward return inside one regime; $A$ is trading days per year; and $h$ is the horizon. The square-root factor converts a per-window ratio to an annual value because there are $A/h$ non-overlapping windows in a year. The calculation subtracts no risk-free rate, so it is a raw return-to-risk ratio, not a true Sharpe ratio.

Trap in that scaling

The $\sqrt{A/h}$ factor is valid only for non-overlapping windows. Here, a 20-day forward return is computed on every trading day, so consecutive rows share 19 of 20 days. The standard deviation $s_h$ therefore uses dependent observations and is not the standard deviation of independent 20-day outcomes. The printed annual value can rank regimes because every regime is treated the same way, but it should not be compared with a published Sharpe ratio.

18Limitations

The descriptive layer uses smoothed labels, which see the future

This is a structural limitation, not a bug.

In descriptive_pipeline.run_pipeline_for_symbol, both models are fitted on the full sample, and the Markov model labels the full sequence with Viterbi decoding. A filtered label for day $t$ uses only $x_1,\ldots,x_t$. A smoothed label uses $x_1,\ldots,x_T$, including days after $t$. The forward-backward quantities that drive the fit are $\gamma_t(k)=\Pr(z_t=k\mid x_{1:T})$, where $T$ is the sample's last day, not day $t$. The parameters $\mu_k$, $\Sigma_k$, and $A$ are also estimated from all $T$ days.

As a result, forward_returns_by_regime reports a Sharpe ratio of $0.33$ in regime 4 and $-0.55$ in regime 3, while predictive_regression reports coefficients for regime indicator variables with p-values below 0.01. These are not achievable results. Acting on a regime-4 label in 2013 would require the 2024 data that helped create it. Read them as outcomes for days grouped together after the fact, not as forecasts.

Why it was not fixed here. Filtered labels would require refitting at every date and rewriting every downstream statistic. That is a research redesign, not a defect repair. The walk-forward layer already asks the same question without this leakage: models use embargoed past data, the scaler uses training rows only, and the Markov path keeps only the last Viterbi state.

The demo data is synthetic, but the generated summary does not say so

See section 13. In short, the tracked data/raw/ files have a fixed ten-point delta grid, two permanent expiries, no COVID crash, and a correlation of $-0.047$ between implied and subsequent realized volatility. Every number in outputs/reports/walkforward/ and in the blog/ folder is a correct computation on a series with no predictable structure. README.md calls them "Portable Demo Data"; the auto-generated research_summary.md presents the same numbers as research findings without the caveat, and that is the file a casual reader opens.

The report has no statistical significance tests

The report gives point estimates only. With 20-day overlapping targets, consecutive errors share 19 of 20 returns, so 1,332 forecasts provide roughly 66 independent observations. A root mean squared error difference of 0.00001—the gap between the regime model and historical mean for SPX—is well within the noise. Without a Diebold-Mariano style test (a forecast-error comparison) and an overlap-robust standard error, read the ranking in research_summary.md as "indistinguishable", not as a reliable order. The methodology document says this; the summary file does not.

The Markov model finds states that are not market states

In the descriptive SPX run, two of the five selected states last about one day on average (1.00 and 1.02), covering 398 and 407 days. The transition matrix sends state 1 to state 2 with probability 1.0 and state 2 back to state 1 with probability 0.968. This is a two-cycle noise pattern: the model alternates between the two states. It is not a regime. The code reports it with the same human-readable names ("Normal", "High-Skew Crash Fear") used for persistent states, which invites over-interpretation. Names in REGIME_NAMES use volatility rank only; nothing shows that state 2 represents crash fear.

What the walk-forward layer still does not cover
  • No transaction costs, capacity, or execution. This forecasts a number; it does not simulate a trade.
  • Hard regime assignment. The forecast uses only the most likely regime and discards the probability that today is borderline. A probability-weighted average of regime means would use more information.
  • One horizon and feature set by default. The shipped configuration runs $h=20$ and atm_term only. Other horizons are untested.
  • Expanding window only. The rolling-window split builder exists and is tested but is never called, so the project does not show whether a fixed-length history would do better.
  • Regime count re-selected at every step. The number of regimes can change between consecutive splits, so "regime 1" in 2020 and "regime 1" in 2023 may describe different groups even after volatility ordering.
