Volatility surface regimes: reading the code

What this repository does, how the pieces connect, what each setting changes, and where the results should and should not be believed.

How to use this

Sections follow execution order. Every code snippet is copied unedited from the file named above it. Every number in a Sample data box was printed by running this repository's own code on the tracked files in data/raw/ on 2026-08-10 — none of them are estimates. Coloured boxes flag design choices, traps and weaknesses.

The project in plain English

An option chain tells you what the market is charging for insurance today. This project turns each day's chain into seven numbers describing the shape of that pricing, groups the days into a small number of unlabelled "states" using a statistical clustering model, and then asks one narrow question: if you know today's state, can you forecast how bumpy the index will actually be over the next month better than four simpler rules can? It answers that question twice — once loosely on the whole history for description, and once strictly, retraining only on the past at every step, for an honest out-of-sample score.

01The question, and the two layers that answer it

The repository is built around one sentence from README.md:

In plain words

Do hidden "states" in the shape of the option-implied volatility surface help you forecast how volatile the index will actually be next month, better than simple rules already do?

Two code paths answer it, and they answer different things.

LayerEntry pointWhat it doesCan its numbers be traded on?
Descriptivepipelines/descriptive_pipeline.py Fits regimes once on the entire history, then describes each regime: how long it lasts, what the surface looks like inside it, what returns followed it. No The labels were built with knowledge of the whole sample. See limitations.
Walk-forwardwalkforward/engine.py Steps through time. At each step it refits everything on past data only, forecasts the next five days, and records the error. In principle The leakage controls are real. The data it currently runs on is not.
Terms used throughout

Implied volatility (IV) — the volatility number that makes an option pricing formula match the option's market price. It is the market's forecast of future movement, in annualized percent.
At-the-money (ATM) — near where the option's delta is $0.50$ in absolute value, roughly a coin flip on finishing in the money.
Delta — how much the option price moves per one-dollar move in the index. Calls have positive delta, puts negative. It is used here as a scale-free way to say "how far from at-the-money", so the same feature means the same thing whether the index is at 1,000 or 5,000.
Realized volatility (RV) — the volatility that actually happened, measured after the fact from daily returns.
Regime — a group of days that a clustering model decided look alike. Nothing more. The model is never told what a regime means.
Look-ahead (leakage) — using information in a forecast that would not have been available at the moment the forecast was supposedly made.

02Where the settings live — config.toml and walkforward.toml

There are two configuration files at the repository root, and the split is deliberate: config.toml owns anything shared (which symbols, which dates, how a feature is defined, how the data cache behaves), and walkforward.toml owns the experiment (horizons, minimum training length, step size, output folder). When the walk-forward command runs, it reads both and pastes the experiment's date window over the shared one:

    merged_data_config["end_date"] = str(sample_config["end_date"])

Trap

An empty fixed_k_values does more than skip the fixed-count sweep. In run_research, include_robustness_models = fixed_k_values is not None, and main() converts an empty list to None. So the default run produces no Hidden Markov Model rows at all, even though the model is fully implemented and tested. If you want the HMM, you must put a value in fixed_k_values.

04Data in — data_access/loader.py

In plain words

Read the option chain and the daily closing prices. Prefer the files already sitting in data/raw/; only reach for the database if those files are missing or fail their integrity checks.

What it does

Input: a symbol, a start and end date, and the [cache] settings. Output: two DataFrames — options with nine columns, prices with date and close. Role: the only place in the repository that touches storage. Everything downstream receives clean frames and never knows where they came from.

The offline check is not just "does the file exist". _build_cache_validation_result runs four gates in order and stops at the first failure:

  1. Version — the sidecar's metadata_version must equal the configured one.
  2. Schema — the sidecar's column list, the Parquet file's column list and their data types must all agree, and each type must be on an allow-list.
  3. Row count — the sidecar's recorded count must equal the actual number of rows.
  4. Date coverage — the sidecar's recorded first and last date must match the file, and must span the whole window you asked for.

Why the duplicate rule is written this way

SPX and SPXW are two ticker symbols for overlapping contracts. _normalize_options_dataframe sorts by (trade_date, expiry_date, option_type, strike_price, open_interest) with open interest descending, then keeps the first row of each group. So when two feeds disagree about the same contract, the more heavily held one wins, which is the better-quoted one.

Trap

The database fallback is wrapped so that a failure produces a message naming the exact folder, the exact filenames and the underlying database error, rather than a bare connection stack trace. That matters because the common failure is a fresh clone with a valid cache and no .env, and the message has to tell you that nothing is actually wrong.

05Features — features/surface.py

In plain words

Squash a whole day's option chain down to seven numbers: how expensive insurance is, how much more expensive downside insurance is than upside, how curved the pricing is across strikes, and how the price of insurance changes as you go further out in time.

What it does

Input: the cleaned options frame. Output: a DataFrame indexed by trade_date with seven float columns, in this order: atm_iv_near, skew_near, butterfly_near, atm_iv_mid, skew_mid, butterfly_mid, term_slope. Role: this is the state vector that every regime model clusters on.

How it works

For each trade date, _select_expiry picks one near-term expiry (the one whose days to expiry is closest to 30, from within the 15–45 window) and one mid-term expiry (closest to 90, within 45–120). For each of those two expiries, _extract_features_one_expiry reads three numbers off the chain by interpolating in delta space. The seventh feature is simply the difference between the two at-the-money readings.

The formula

Let $\sigma(\Delta)$ be implied volatility at delta $\Delta$, read off one expiry's chain. Between two quoted strikes it is interpolated in a straight line:

$$\sigma(\Delta)=\sigma_{\text{lo}}+\bigl(\sigma_{\text{hi}}-\sigma_{\text{lo}}\bigr)\cdot \frac{\Delta-\Delta_{\text{lo}}}{\Delta_{\text{hi}}-\Delta_{\text{lo}}}$$

The four features per expiry, with $a$ the setting atm_delta and $w$ the setting wing_delta:

$$\begin{aligned} \mathrm{atm\_iv} &= \sigma(-a) \\ \text{skew} &= \sigma(-w)-\sigma(+w) \\ \text{butterfly} &= \tfrac{1}{2}\bigl[\sigma(-w)+\sigma(+w)\bigr]-\sigma(-a) \\ \mathrm{term\_slope} &= \mathrm{atm\_iv}_{\text{mid}}-\mathrm{atm\_iv}_{\text{near}} \end{aligned}$$

$\Delta_{\text{lo}}$ and $\Delta_{\text{hi}}$ are the quoted deltas immediately below and above the one requested, and $\sigma_{\text{lo}},\sigma_{\text{hi}}$ their implied volatilities. Negative deltas are puts, positive are calls, so $\sigma(-a)$ is read off the put side and $\sigma(+w)$ off the call side. Skew is positive when downside protection costs more than upside, which is the normal shape for equity indices. Butterfly is positive when the wings cost more than a straight line between them would suggest, meaning the market is paying extra for large moves in either direction. Term slope is positive when longer-dated insurance costs more than short-dated, the calm-market shape.

Why delta space and not strike space

A strike of 1,060 means something completely different in 2010 than in 2024. A delta of $-0.50$ means the same thing in both. Working in delta makes the seven features comparable across the whole sample, which is the only reason clustering fifteen years of days together is defensible at all.

Trap

interpolate_iv_at_delta returns NaN rather than extrapolating when the requested delta lies outside the quoted range. That is the right choice — extrapolated wing volatility is fiction — but it means a thin chain silently produces a blank feature row, which both pipelines then drop. A run that quietly loses a third of its days looks identical to a run that loses none unless you check the log line Feature extraction complete: N days, M valid.

The feature-set registry

FEATURE_SET_REGISTRY names five fixed column subsets so an experiment can be requested by name. select_feature_columns looks the name up, checks every required column is present, and returns them in registry order. Order matters: several downstream steps locate the at-the-money column by position.

06The forecast target — walkforward/targets.py

In plain words

For every trading day, work out how volatile the index actually turned out to be over the following twenty trading days. That is the thing every model is trying to guess.

What it does

Input: the price frame, the feature frame (used only for its index and its atm_iv_near column), a horizon $h$ and an annualization factor $A$. Output: a frame on the feature index with realized_vol, variance_risk_premium and forward_return. Role: supplies the "right answer" that every forecast is scored against.

The formula

$$r_t=\log\!\left(\frac{P_t}{P_{t-1}}\right)$$

$$\mathrm{RV}_t(h)=\operatorname{std}\bigl(r_{t+1},\,r_{t+2},\,\ldots,\,r_{t+h}\bigr)\times\sqrt{A}$$

$$\mathrm{VRP}_t=\sigma^{\mathrm{ATM}}_t-\mathrm{RV}_t(h),\qquad \mathrm{fwd\_ret}_t=\frac{P_{t+h}}{P_t}-1$$

$P_t$ is the closing index level on trading day $t$; $r_t$ is that day's log return; $h$ is the horizon in trading days (default 20); $A$ is trading days per year (252); $\operatorname{std}$ is the ordinary sample standard deviation with $h-1$ in the denominator, which is what pandas.rolling().std() computes; $\sigma^{\mathrm{ATM}}_t$ is atm_iv_near on day $t$. The variance risk premium here is the ex-post gap between what the market charged for volatility and what volatility turned out to be — positive means insurance was expensive relative to what happened.

The one line that does the alignment

log_returns = np.log(close_series / close_series.shift(1))
rolling_std = log_returns.rolling(window=horizon).std()
annualized_vol = rolling_std * np.sqrt(float(annualization))

# Shift the trailing window backward so the value lands on the start date
# of the forward-looking window.
forward_realized_vol = annualized_vol.shift(-horizon)

rolling(20).std() naturally produces a backward-looking number: on day $t$ it is the standard deviation of $r_{t-19}\ldots r_t$. Shifting by $-20$ moves that value 20 rows earlier, so it now sits on day $t-20$ and describes $r_{t-19}\ldots r_t$, which are the twenty returns after $t-20$. Renaming the index, the value on day $t$ describes $r_{t+1}\ldots r_{t+h}$, exactly as the formula says.

Trap

Because the target is built by shifting, the last $h$ rows of the panel have no answer and are dropped later by dropna(). Sizing checks must use the number of rows that survive that drop, not the number of feature rows. Getting this wrong is how a walk-forward run silently produces an empty file, which is a mistake this repository has already made once and now guards against explicitly.

07Splits and the embargo — walkforward/splits.py and the engine

In plain words

March forward through the calendar. Train on everything before today, forecast the next five days, then move the wall forward five days and repeat. Then throw away the most recent training days, because their answers were not known yet on the day you are pretending to stand.

Step one: the plain chronological split

splits: list[WalkForwardSplit] = []
train_end = min_train_size

while train_end < len(dates):
    test_start = train_end
    test_end = min(test_start + step_size, len(dates))

    # Training always uses everything strictly before the test window.
    train_index = dates[:train_end]
    test_index = dates[test_start:test_end]
    splits.append(WalkForwardSplit(train_index=train_index, test_index=test_index))

    # Expand the history by the same stride used for testing.
    train_end = test_end

This is an expanding window: the training set only ever grows. A rolling-window builder with a fixed-length history also exists in the same file, but the engine does not currently use it.

Step two: the embargo, which is the part that matters

The formula

Let $i(d)$ be the position of date $d$ in the full sorted price history, $h$ the horizon, and $s$ the first date of the test block. A training row at date $t$ is kept only when

$$i(t)+h \;<\; i(s)$$

The label at $t$ is built from returns $r_{t+1}\ldots r_{t+h}$, so the last price it touches sits at position $i(t)+h$. Requiring that position to fall strictly before $i(s)$ means no training label uses a price observed on or after the first day being forecast. Positions come from the price calendar, not the feature calendar, so a gap in the option data cannot quietly shrink the gap.

Why chronological ordering is not enough on its own

This is the single most important idea in the repository. Suppose you train up to Friday and forecast the following Monday. The training row dated Friday carries a label describing the next twenty trading days — which include that Monday and the three weeks after it. Training on it means the model has already seen the answer to the question you are about to ask. The split looks perfectly chronological and is still contaminated. The embargo deletes the last $h$ training rows to close the overlap.

Sample data

The gap is 20 price days wide, not 20 calendar days.

Across the whole SPX panel of 3,872 aligned rows, the builder proposes 271 splits; after the embargo, 267 of them still have the required 2,520 safe labels, so the first forecast lands on 2019-10-28 rather than 2019-09-30. Those 267 splits carry 1,332 forecast dates per model: 266 full blocks of five, plus a final short block of two, because the panel runs out of dates before the last stride completes. 1,332 is the count in outputs/reports/walkforward/metric_summary.csv.

Trap

min_train_size is checked after the embargo, not before. The split builder is handed the same number, so the first few splits are always proposed and then immediately skipped because they are short by roughly $h$ rows. This is why the first forecast date is about a month later than the naive arithmetic suggests. Before any model is fitted, _maximum_safe_train_size puts the last row in a one-row test set and measures the largest embargoed training set that could ever exist; if that is smaller than min_train_size, the run raises a ValueError naming the symbol, horizon, feature set, aligned row count, maximum and requested minimum — rather than writing an empty CSV.

08The regime models — regimes/latent_models.py

In plain words

Given a cloud of daily feature vectors, find a small number of overlapping blobs that describe the cloud well, and label each day with the blob it most likely came from. Then rename the blobs so that number 0 is always the calmest one.

The Gaussian Mixture Model — fit_gmm

The model

Each standardized daily feature vector $x_t\in\mathbb{R}^d$ is assumed to be drawn from one of $K$ multivariate normal distributions, but you are not told which:

$$p(x_t\mid\theta)=\sum_{k=1}^{K}\pi_k\,\mathcal{N}\!\bigl(x_t\mid\mu_k,\Sigma_k\bigr)$$

$K$ is the number of regimes; $\pi_k$ is the share of days belonging to regime $k$, with $\sum_k\pi_k=1$; $\mu_k$ is that regime's average feature vector; $\Sigma_k$ is its $d\times d$ covariance matrix (the code uses covariance_type="full", so every regime gets its own unrestricted shape); $\mathcal{N}$ is the multivariate normal density; $\theta=\{\pi_k,\mu_k,\Sigma_k\}$ is the whole parameter set. Days are treated as independent draws — the model has no notion of yesterday.

The objective it maximizes

$$\ell(\theta)=\sum_{t=1}^{n}\log\sum_{k=1}^{K}\pi_k\,\mathcal{N}\!\bigl(x_t\mid\mu_k,\Sigma_k\bigr)$$

$n$ is the number of training days. This is the log-likelihood: how probable the observed data is under the parameters. There is no closed-form maximum because you do not know which regime produced each day, so it is maximized iteratively.

The update the loop performs (expectation-maximization)

E step — given the current parameters, work out how much each day belongs to each regime:

$$\gamma_{tk}=\frac{\pi_k\,\mathcal{N}(x_t\mid\mu_k,\Sigma_k)} {\sum_{j=1}^{K}\pi_j\,\mathcal{N}(x_t\mid\mu_j,\Sigma_j)}$$

M step — given those weights, recompute the parameters as weighted averages:

$$n_k=\sum_{t=1}^{n}\gamma_{tk},\qquad \pi_k=\frac{n_k}{n},\qquad \mu_k=\frac{1}{n_k}\sum_{t=1}^{n}\gamma_{tk}\,x_t$$

$$\Sigma_k=\frac{1}{n_k}\sum_{t=1}^{n}\gamma_{tk}\,(x_t-\mu_k)(x_t-\mu_k)^{\top}$$

$\gamma_{tk}$ is the responsibility of regime $k$ for day $t$, a number between 0 and 1 with $\sum_k\gamma_{tk}=1$; $n_k$ is the effective number of days in regime $k$; $\top$ is matrix transpose. The two steps alternate until the log-likelihood stops rising. Each step is guaranteed not to lower the log-likelihood, but the result depends on where you start, which is why the code passes n_init=5 and random_state=42 — five starting points, best one kept, same answer every run.

Choosing the number of regimes

The code fits every $K$ from min_k to max_k and keeps the one with the lowest Bayesian information criterion:

$$\mathrm{BIC}(K)=p_K\log n-2\,\ell_K,\qquad p_K=(K-1)+Kd+K\frac{d(d+1)}{2}$$

$\ell_K$ is the best log-likelihood reached with $K$ regimes; $p_K$ counts the free parameters — $K-1$ mixing weights, $Kd$ mean entries, and $K$ symmetric covariance matrices of $d(d+1)/2$ distinct entries each. The $p_K\log n$ term is a fine for complexity, so extra regimes must earn their keep. Lower is better.

The Hidden Markov Model — fit_hmm

The model, its objective, and its update

Model. A hidden state $z_t\in\{1,\ldots,K\}$ moves according to a transition matrix, and the observed features are normal around that state's mean:

$$\Pr(z_{t+1}=j\mid z_t=i)=A_{ij},\qquad x_t\mid z_t=k\;\sim\;\mathcal{N}(\mu_k,\Sigma_k)$$

Objective. The same idea as before, but the sum now runs over whole state paths:

$$\ell(\theta)=\log\sum_{z_1,\ldots,z_T}\Pr\bigl(z_1,\ldots,z_T,\;x_1,\ldots,x_T\mid\theta\bigr)$$

Update (Baum-Welch, which is expectation-maximization for this model). A forward-backward pass gives $\gamma_t(k)=\Pr(z_t=k\mid x_{1:T})$ and $\xi_t(i,j)=\Pr(z_t=i,z_{t+1}=j\mid x_{1:T})$; the parameters are then re-estimated as

$$A_{ij}=\frac{\sum_{t=1}^{T-1}\xi_t(i,j)}{\sum_{t=1}^{T-1}\gamma_t(i)},\qquad \mu_k=\frac{\sum_{t=1}^{T}\gamma_t(k)\,x_t}{\sum_{t=1}^{T}\gamma_t(k)}$$

$T$ is the sequence length; $A_{ij}$ is the probability of moving from state $i$ to state $j$ in one day; $\gamma_t(k)$ is the probability that day $t$ was in state $k$; $\xi_t(i,j)$ the probability that day $t$ was in $i$ and day $t+1$ in $j$. Both quantities condition on the whole sequence $x_{1:T}$, including days after $t$. That word "whole" is the source of the look-ahead problem discussed in limitations.

The code runs the fit n_restarts times with different random seeds, scores each on in-sample log-likelihood, and keeps the best. Restarts that blow up are logged as warnings and skipped; if every restart fails it raises RuntimeError. Labels come from Viterbi decoding, which returns the single most likely state path rather than the most likely state on each day independently.

Trap: most of those restarts do not survive

The except Exception around each restart is doing far more work than it looks. Running the descriptive pipeline on SPX with the shipped settings — five states, ten restarts — prints this:

Fixing label switching — order_regimes_by_volatility

Why this function has to exist

Nothing forces a clustering model to call the calm blob "0". Refit the same data with a different random seed and the same blob might come back as "1". Any statistic reported per label would then be meaningless across fits. This function computes each label's average standardized atm_iv_near, sorts them, and renumbers so 0 is always the lowest-volatility regime. Only after this renaming is a regime label comparable across splits, across symbols and across runs.

09The five forecast rules — walkforward/models.py

In plain words

Five ways of answering "how volatile will the next month be?", ranging from "just read today's option price" to "figure out which regime we are in and use that regime's historical average".

Row nameRuleUsesWhy it is in the panel
atm_iv$\hat y_t=\sigma^{\mathrm{ATM}}_t$today's option price only The market's own published forecast. The obvious thing to beat.
historical_mean$\hat y_t=\dfrac{1}{|\mathcal{T}_t|}\sum_{u\in\mathcal{T}_t}y_u$past labels only The hardest benchmark to beat and the easiest to forget. If a clever model cannot beat a flat line, it has added nothing.
trailing_realized_vol$\hat y_t=\operatorname{std}(r_{t-h+1..t})\sqrt{A}$past prices only Tests whether volatility simply persists.
linear_featuresordinary least squares on the selected featurespast features and labels Tests whether the surface helps at all, before any regime machinery.
gmm_regime_mean$\hat y_t=\bar y^{(\hat z_t)}$past features and labels The actual research claim.
The formula for the regime forecast

$$\hat y_t=\frac{1}{\bigl|\{u\in\mathcal{T}_t:\hat z_u=\hat z_t\}\bigr|} \sum_{u\in\mathcal{T}_t,\;\hat z_u=\hat z_t}y_u$$

$\mathcal{T}_t$ is the embargoed training window available on day $t$; $y_u$ is the realized-volatility label for training day $u$; $\hat z_u$ is the ordered regime assigned to training day $u$; $\hat z_t$ is the ordered regime assigned to the day being forecast. In words: find which regime today looks like, then predict the average outcome that followed days that looked like that. If today's regime cannot be mapped into the ordered space, the code falls back to the plain training mean and records the regime as $-1$.

How the block fit works

train_feature_matrix = train_features.to_numpy(dtype=float)
standardized_train_features, fitted_scaler = standardize_features(
    feature_matrix=train_feature_matrix
)
ordered_test_features = test_features.reindex(columns=train_features.columns)
standardized_test_features = fitted_scaler.transform(
    ordered_test_features.to_numpy(dtype=float)
)
Why the scaler is fitted and then reused, never refitted

Standardizing means subtracting a mean and dividing by a standard deviation. If those two numbers were computed over the training and test rows together, every test row would leak a little information about itself into the training data. Fitting on training rows only and calling .transform() on the test rows keeps the boundary intact. On the first window the fitted values are mean [0.14023, 0.16224, 0.02202] and scale [0.03557, 0.03558, 0.00251]; every test row is scaled by those, whatever it contains.

Why one fit per block instead of one per day

Every one of the five test days in a block shares exactly the same training window, so refitting five times would produce five identical models. Fitting once is not an approximation — it gives the same answer for the linear model and the mixture model, five times faster.

Trap the Hidden Markov Model path avoids

The mixture model can classify each test day independently, but a Markov model reads sequences, so it needs context. The naive shortcut is to decode the whole training block plus the whole test block at once. That would let Wednesday's observation influence Monday's state. Instead the code decodes the training sequence plus one test row at a time and keeps only the final state:

predicted_test_labels = np.asarray(
    [
        int(
            fitted_model.predict(
                np.vstack([standardized_train_features, test_feature_row])
            )[-1]
        )
        for test_feature_row in standardized_test_features
    ],
    dtype=int,
)

Taking element [-1] is what makes this safe: the last state of a Viterbi path depends only on observations up to and including that point, because there is nothing after it. It is slow — one decode per test day — and that cost is the price of the guarantee.

10The engine loop — walkforward/engine.py

In plain words

Four nested loops: for each symbol, for each horizon, for each feature set, for each time step — fit, forecast, write down five rows per day.

What it does

Input: the experiment grid and the shared config. Output: three files in outputs/reports/walkforward/. Role: the only place that decides what a "run" means.

The order of operations, once per symbol and horizon

  1. Load options and prices, build the seven features, drop blank rows.
  2. Build the forward targets and the trailing-volatility benchmark on the feature index.
  3. Join features, target and benchmark into one frame and dropna(). Every model now sees exactly the same dates — this is what makes the error comparison fair.
  4. Check capacity. If the largest possible embargoed training set is smaller than min_train_size, raise a ValueError and stop before fitting anything.
  5. Build the expanding splits; for each, apply the embargo and skip the split if too few safe labels remain.
  6. Fit the linear model and the mixture model once for the block; compute the historical mean once.
  7. Walk the test rows and append five standardized dictionaries per row.
Why the shared aligned panel matters more than it looks

Step 3 is the difference between a real comparison and a misleading one. If the trailing-volatility benchmark had a few extra dates because it needs fewer inputs, it would be scored on a slightly different sample and its root mean squared error would not be comparable to the others. Joining first and dropping blanks once forces every model onto an identical date set.

Trap

OUTPUT_DIR is a module-level global. main() reassigns it from walkforward.toml before calling run_research, and run_research reads the global rather than taking a parameter. If you import run_research and call it yourself — as the tests and the notebook do — the output_dir setting in walkforward.toml is ignored and results go to the default folder.

11Scoring — walkforward/reporting.py

The formulas

For $N$ forecast dates with actual values $y_t$ and forecasts $\hat y_t$:

$$\mathrm{MSE}=\frac{1}{N}\sum_{t=1}^{N}\bigl(y_t-\hat y_t\bigr)^2,\qquad \mathrm{RMSE}=\sqrt{\mathrm{MSE}},\qquad \mathrm{MAE}=\frac{1}{N}\sum_{t=1}^{N}\bigl|y_t-\hat y_t\bigr|$$

And, for a model $m$ against a benchmark $b$ measured on identical dates:

$$R^2_{\mathrm{OOS},\,m\mid b}=1-\frac{\mathrm{MSE}_m}{\mathrm{MSE}_b}$$

$\mathrm{MSE}$ is mean squared error, $\mathrm{RMSE}$ its square root (back in volatility units), $\mathrm{MAE}$ mean absolute error. $R^2_{\mathrm{OOS}}$ is positive when the model has smaller squared error than the benchmark, zero when they tie, and negative — unbounded below — when the model is worse. It is not the $R^2$ of a regression and it is not confined to $[0,1]$.

The function groups the panel by (symbol, horizon, feature_set, model_name) and computes each benchmark's mean squared error over the matching (symbol, horizon, feature_set) group, so a model is only ever compared with a benchmark scored on the same dates. Two benchmarks are reported: atm_iv and historical_mean.

Why two benchmarks and not one

Scoring only against implied volatility flatters everything. Implied volatility is a biased forecast — it is systematically higher than realized volatility because it carries a risk premium — so almost any unbiased rule beats it. The expanding historical mean has no such bias, which makes it the honest hurdle. In the run stored under outputs/ every model clears the first hurdle by a wide margin and none clears the second.

Trap in the markdown summary

write_research_summary sorts the whole table by root mean squared error and prints the top ten. Root mean squared error is in units of the target, so a 5-day horizon and a 60-day horizon — or two different indices — are not on the same scale. With a single symbol and horizon the ranking is fine; add a second horizon and the "best configurations" table starts comparing things that cannot be compared.

12The descriptive layer — descriptive/analytics.py

In plain words

Fit the regimes once on all fifteen years, then describe them: how many days each holds, how long it lasts, how expensive insurance was inside it, and what the index did next.

The pipeline fits a mixture model to choose the regime count, fits a Markov model with that count, renames the states by volatility level, recomputes the transition matrix from the renamed path, and then hands the labels to six reporting functions.

FunctionProduces
regime_summary_statsmean and standard deviation of every feature inside each regime, plus day counts and shares
regime_vrp_statsaverage variance risk premium per regime with a 95% interval, $\bar x \pm 1.96\,s/\sqrt{n}$
regime_transition_statsaverage unbroken run length per regime, total number of switches, switch rate
predictive_regressionordinary least squares of forward realized volatility on ATM implied volatility plus regime dummy variables, with the lowest regime as the omitted baseline
forward_returns_by_regimemean, standard deviation and annualized Sharpe ratio of the $h$-day forward return inside each regime
_recompute_transition_matrix_from_labels
lives in pipelines/descriptive_pipeline.py, not in analytics.py		counts one-step transitions on the renamed path and normalizes each row
The Sharpe formula used here

$$\mathrm{Sharpe}=\frac{\bar R_h}{s_h}\sqrt{\frac{A}{h}}$$

$\bar R_h$ and $s_h$ are the mean and standard deviation of the $h$-day forward return inside one regime; $A$ is trading days per year; $h$ is the horizon. The square-root factor converts a per-window ratio into a per-year one, because there are $A/h$ non-overlapping windows in a year. No risk-free rate is subtracted, so this is a raw return-to-risk ratio rather than a true Sharpe ratio.

Trap in that scaling

The $\sqrt{A/h}$ factor is the right conversion only if the returns being averaged come from windows that do not overlap. They do overlap here: a 20-day forward return is computed on every trading day, so two consecutive rows share 19 of their 20 days. The standard deviation $s_h$ is therefore measured on strongly dependent observations and is not the standard deviation of independent 20-day outcomes. The annual figure the code prints is a reasonable ranking device across regimes, because every regime is treated the same way, but it is not a number you could compare with a published Sharpe ratio.

Every number in that table was computed from labels produced by a model that had already seen the entire sample, so none of them is a trading result. The average forward Sharpe of $0.33$ in regime 4 does not mean you could have earned it; you would have needed to know in 2012 how the model would label 2023. Section 18 spells this out.

Why you should not believe that as a market finding

The tracked files in data/raw/ are synthetic demo data, not real market history. Running the code prints the evidence:

  • Option deltas take exactly ten values, $\pm0.2,\pm0.3,\pm0.4,\pm0.5,\pm0.6$, on every one of 3,912 days. Real chains have hundreds of irregular strikes.
  • There are exactly two expiries per day, at 30 and 90 days, forever. Real expiry calendars roll.
  • Exactly 20 rows per trade date, with volume and open interest running in arithmetic sequences.
  • "SPX" ranges from 674.91 to 1617.69 across 2010–2024 and closes 2024-12-31 at 1073.08. The real index was near 1,100 in early 2010 and near 5,900 at the end of 2024. On 2020-03-23, the deepest day of the COVID sell-off, this series prints 1596.51 — near its all-time high, with no crash anywhere in it.
  • On the aligned panel, the correlation between today's ATM implied volatility and the next month's realized volatility is -0.047, and between trailing and forward realized volatility -0.065. In real equity index data both are strongly positive; volatility clusters. This series has no volatility clustering at all.

So "the historical mean wins" is a true statement about a series that was constructed with no predictable structure. It verifies that the pipeline is not manufacturing skill out of noise — which is a genuinely useful thing to know — but it is not evidence about implied volatility. The README.md is upfront that these are "Portable Demo Data"; the generated research_summary.md is not, and reads like a market result.

17Traps a reader should know about

18Honest limitations

The descriptive layer uses smoothed labels, and smoothed labels see the future

This is the most important caveat in the repository, and it is structural rather than a bug.

In descriptive_pipeline.run_pipeline_for_symbol, both models are fitted on the entire sample, and the Markov model's labels come from Viterbi decoding the entire sequence at once. A filtered label for day $t$ would use only $x_1,\ldots,x_t$. A smoothed label uses $x_1,\ldots,x_T$ — the whole history, including everything after $t$. Formally the forward-backward quantities that drive the fit are $\gamma_t(k)=\Pr(z_t=k\mid x_{1:T})$, and $T$ is the last day of the sample, not day $t$. On top of that, the parameters $\mu_k$, $\Sigma_k$ and $A$ were themselves estimated from all $T$ days.

The practical consequence: forward_returns_by_regime reports a Sharpe ratio of $0.33$ in regime 4 and $-0.55$ in regime 3, and predictive_regression reports regime dummy coefficients with p-values below 0.01. None of these is achievable. To act on a regime-4 label in 2013 you would have needed the 2024 data that helped produce it. The correct reading is "days the model retrospectively grouped together also had these outcomes", which is a description, not a forecast.

Why it was not fixed here. Converting the descriptive layer to filtered labels means refitting at every date and rewriting every downstream statistic — that is a research redesign, not a defect repair, and the repository already contains the leakage-safe version of the same question in the walk-forward layer. The walk-forward layer is clean: models are fitted on embargoed past data only, the scaler is fitted on training rows only, and the Markov path takes only the last Viterbi state so no future observation exists to condition on.

The demo data is synthetic, and the generated summary does not say so

Detailed in section 13. The short version: the tracked data/raw/ files have a fixed ten-point delta grid, two permanent expiries, no COVID crash, and a correlation of $-0.047$ between implied and subsequent realized volatility. Every number in outputs/reports/walkforward/ and in the blog/ folder is a correct computation on a series with no predictable structure. README.md calls them "Portable Demo Data"; the auto-generated research_summary.md presents the same numbers as research findings with no such caveat, and that file is what a casual reader opens.

The statistical tests that are not there

The report gives point estimates only. With 20-day overlapping targets, consecutive errors share 19 of 20 returns, so 1,332 forecasts carry roughly 66 independent observations. A difference in root mean squared error of 0.00001 — which is the gap between the regime model and the historical mean for SPX — is far inside the noise. The absence of a Diebold-Mariano style test with an overlap-robust standard error means the ranking in research_summary.md should be read as "indistinguishable" rather than "in this order". The methodology document does state this; the summary file does not.

The Markov model finds states that are not market states

On the descriptive SPX run the selected five states include two whose average unbroken run length is about one day (1.00 and 1.02), holding 398 and 407 days between them, with a transition matrix that sends state 1 to state 2 with probability 1.0 and state 2 back to state 1 with probability 0.968. That is a two-cycle absorbing noise, not a regime. The code reports it in the same table and with the same human-readable names ("Normal", "High-Skew Crash Fear") as the genuinely persistent states, which makes it easy to over-read. Those names in REGIME_NAMES are assigned purely by volatility rank — nothing verifies that state 2 has anything to do with crash fear.

What the walk-forward layer still does not cover
  • No transaction costs, no capacity, no execution. This forecasts a number; it does not simulate a trade.
  • Hard regime assignment. The forecast uses the single most likely regime, discarding the probability that today is a borderline case. A probability-weighted average of regime means would use strictly more information.
  • One horizon, one feature set by default. The shipped configuration runs $h=20$ and atm_term only. Conclusions about other horizons are untested.
  • Expanding window only. The rolling-window split builder exists and is tested but is never called, so there is no evidence on whether a fixed-length memory would do better.
  • Regime count re-selected at every step. The number of regimes can change between consecutive splits, so a "regime 1" in 2020 and a "regime 1" in 2023 need not describe the same thing even after volatility ordering.
